## Pipeline

1. **Vision:** petri dish (pebbles, dry noodles, seeds, crumbs; ~1–20 mm) photographed; objects measured by size. The "real" system would use an automated microscope, but for the demo objects the team's iQCrew microscope zooms in too far (tested 2026-10-24), so the demo uses an overhead camera (phone or USB webcam, still to be chosen) with a backlight. The microscope's camera is an AmScope MD300A: plain UVC, camera index 1 on this laptop, 2048×1536, no vendor software needed (`vision/live_view.py` shows it with a focus meter).
2. **Planner:** sizes → which of the 5 filters go into the 3 rig slots (coarse-to-fine order is a rule) → list of moves.
3. **Arm:** SO-101 follower moves filters between the rig and a side storage shelf.

**Closed loop (user's design, 2026-10-24):** the demo sample will likely be about two layers with pile-up, so per-object measuring of the first photo won't work. Instead:
- First photo of the pile → rough estimate of which of the 9 types are present and how much (patch classifier on colour/texture, trained from single-type photos, plus a per-type reference size table) → first 3 filters chosen **coarse-first**, targeting the largest common objects.
- Each time the robot changes a filter it photographs that filter's catch (recommended: a fixed inspection spot under the overhead camera, so the calibration holds) → identify the catch → update the sample estimate → re-plan the next filter change.
- Every capture is logged (run, step, filter, and the size band it implies: caught by hole h_i, passed h_{i-1}). The filters act as free size labels for training, and the band is a consistency check on the classifier (e.g. "rice" on a 5–8 mm filter is impossible), so retraining on new captures doesn't reinforce its own mistakes.
- Limits: the camera sees only the top layer, and shaking makes small items sink. Piles need front lighting (colour); a backlight would turn a pile into one shadow.
- Open questions: what happens to a catch after it's photographed (re-poured? by whom?); what the filter mesh looks like as a photo background.

## Gotchas

- Only one program can open a COM port; stop teleoperation before probing.
- Stopping teleoperation disables follower torque: it drops if unsupported.
- Paths under the Claude temp/scratchpad folder exceed Windows MAX_PATH; Python and PowerShell 5.1 fail on them. Run scripts from short paths.
- Ruler-tick detection for scale is unreliable (glare, scratches); prefer a fixed camera height or a printed square of known size.

## Arm design decisions

- Movement mostly scripted: tight fixtures (rails, back stop, chamfered slot openings, self-centring handle on each filter) + teach-and-repeat poses recorded with the leader. A learned policy (ACT) is a stretch goal, not the critical path.
- Free checks from motors: gripper closes fully = missed grab; load spike on insert = jam → back off and retry.
- Wrist camera (USB webcam) with ArUco markers: final-approach alignment, filter identity / seated check, startup inventory sweep.
- Each filter has a fixed home slot in storage (5 spots). Worst case 6 pick-and-place moves per reconfiguration.
- A hand-typed plan is the demo-day fallback if vision fails.
- Microcontroller (user wants one): optional and off the critical path, USB serial text protocol, system must run with it unplugged. Ideas: status screen (user's first pick, deferred), per-slot status LEDs, slot-seated sensors, start button, backlight box for the dish. Real e-stop = inline power switch on the follower's 12 V supply.

## Wrist camera and filter markers (2026-10-25)

- Wrist camera = **"USB2.0_CAM1"** (1920×1080, open with `--camera CAM1`). "USB2.0 FHD UVC WebCam" is the laptop's built-in camera. Not mounted on the arm yet; `wrist_camera` in layout.json is already "CAM1" (routines carry on without it if it's unplugged or busy, e.g. the live view has it open). Test photos go to `vision/captures/wrist/`.
- Arm marker checks (motion.py, 2026-10-25, tested with a stand-in camera and the practice arm only): `look` step at `<slot>/front` before every pick reads the marker nearest the image centre; a different filter than the one asked for (`pick SLOT A|F1`) raises WrongFilter there, gripper open; no marker seen = warn and carry on (missed-grab check covers an empty slot). `scan` visits every front pose (back to carry between slots) and records no marker as empty. `took`/`put` steps keep `arm/inventory.json` (git-ignored): slot missing = not checked, null = empty, "?" = unreadable. Assumes the camera sees the filter's marker from the front pose with the gripper open; unverified until it's mounted. Inventory is meant as the move planner's "where is each filter" input. A filter is in one place only: seeing it in a slot clears it from other slots (back to not checked) and turns a matching `holding` into "?".
- Real-camera practice run (2026-10-25, hand-held camera on filter A): `pick rig/top A` went in, `pick rig/middle B` stopped in front, scan read A in 5 of 6 views. The miss was a steep top-down view: the marker (on the filter's side face) became a blurry, overexposed ~90×30 px strip; looser detector settings didn't help. So the front pose must see the marker face fairly square-on. That photo also showed the filter: white plastic, holes in 6 patches, so pale objects (rice, macaroni, yellow balls) will have little contrast in catch photos.
- It will photograph each pulled filter's catch (user, 2026-10-25; replaces the inspection spot under the overhead camera) and read the filter's marker. Catch photos need their own training set: different scale, lighting and background (the mesh) than the dish photos.
- Filter codes: printed ArUco DICT_4X4_50, A–E = ids 1–5 (`markers` in filters.json; D/E for F4/F5). `vision/markers.py sheet` writes `vision/filter_markers.pdf` (US Letter, 15/20/25 mm, dotted cut line outside the one-cell white margin); `read IMAGE` lists the filters found. All 15 read back from the rendered sheet down to 2.5 px/mm and with tilt. The team's hand-drawn codes didn't read (thin outline, no thick black border, blobby cells). At desk distance the wrist camera saw them ~140 px across, so even 15 mm markers have plenty of pixels.

## Teach and repeat (arm/, built 2026-10-25, tested only in practice mode so far)

- The rig is built (user, 2026-10-25): an upside-down T; filter shelf (3 slots) left of the vertical extrusion, storage on the right at the same heights. Storage slot count assumed 3 (`storage/top|middle|bottom`); change in `arm/layout.json` if different.
- `arm/motion.py`: `Arm` sends smooth, speed-limited joint moves (smoothstep, 50 Hz; speeds in layout.json), routines are step lists (`move`, `open`, `close`, `check_grip`, `side`, `leave_side`, `shake`, `wait`, `capture`). Rules: in/out of a slot at slow speed and always back out to `<slot>/front`; switch sides only between the two `carry` poses; missed grab = gripper closed > `missed_grab_at` of open->closed -> open, back out to the previous pose, stop. `connect()` writes Goal_Position = Present_Position before torque comes on (no jump to a stale goal).
- `arm/teach.py`: `teach` (mirror thread, rate-limited 2 deg/tick, so jumps become glides; commands save/todo/list/where/delete/goto/check/pick/place/move/dump/follow/quit), `todo`, `run ...`. `--practice` uses stand-in arm/leader and `practice_poses.json` (git-ignored); `--practice-miss` simulates an empty grab. Poses in `arm/poses.json` (commit them once taught).
- Dish grabbing needs a repeatable dish spot (corner guide); the arm doesn't look for the dish yet. Wrist-camera photo on each pick is wired (`wrist_camera` in layout.json); the size/novelty check on those photos is later work.

## Vision status

Demo objects (updated 2026-10-24): the flat/curved pale pasta in early photos is **not** part of the sample; only short tube macaroni. The sample has **7 types** (user, 2026-10-24). The dark-looking ones are three: the tiny seed (class "dark seed"), the oval seed (class "red seed", dark reddish-brown), and the long seed (class "black grain"). The rest: white rice, oat grain, small yellow grain, short tube macaroni ("pasta tube"). My earlier guesses "small grey seed" / "tiny black seed" were the same tiny seed. Class names in training.json (renamed 2026-10-24): tiny seed, oval seed, long seed, white rice, yellow rice (the elongated beige grain, formerly "oat grain"), macaroni (short tube), yellow balls (the small round yellow balls). Training photos should look like the mix: rice and yellow grain need scattered (not packed) single-type photos. The real demo dish will hold several of each, likely piled.

Dish: 63 mm across; flat floor out to ~24 mm radius, side wall 24–27 mm, rim to ~31.5 mm (consistent across all 3 samples once scale is right).

`vision/ruler_scale.py`: px/mm from ruler mm ticks (autocorrelation spacing, shortest strong peak to avoid the 2x long/short-tick harmonic, then line fit; strips with fit rms > 1 px ignored). Samples: 01 = 9.12, 02 = 12.89, 03 = 11.84 px/mm (02 vs 03 differ 9%: phone height changed).

Webcam (XWF-1080P, 1920×1080) is mounted over the dish on white printer paper. Calibrated 2026-10-24 from `vision/samples/webcam_calibration_ruler.webp` (metal ruler mm ticks): **13.9 px/mm**, stored in `vision/calibration.json` and used by dish_sizer when `--px-per-mm` is omitted; the dish measures ~62 mm, matching the phone photos. The ruler's right end reads ~3% lower, so a slight tilt remains. A ruler under the dish ruins segmentation (metal stripes behind objects, background model skewed); keep it beside the dish, or out of the photo once calibrated. A ruler at the top of the frame read 14.6 px/mm, so expect up to ~5% scale error across the frame until the camera is levelled or calibrated with the ruler where the dish sits.

calibration.json also holds the webcam setup's segmentation settings, applied only when `--px-per-mm` is omitted (explicit flags win): `threshold` 10 (pale yellow on white paper differs by only ~11 colour units; red seed ~53, empty floor ~2) and `floor_mm` 52. Dish finding: Hough was dropped. `fit_rim` brute-forces dish-sized circles (28–34 mm radius) with at least 80% of the rim in frame (the dish often runs off the bottom edge), scoring the **median** gradient across the circle (radial) on a 1/4-size image, then refines at full size. Median, not mean, so circles borrowing part of the ruler's strong straight edge lose. Correct on all 21 samples; ~3 s per photo.

`vision/pile_types.py` (rough per-type estimate for piles): 2.5 mm squares on the dish floor, 13 colour/texture features, OpenCV random forest. Training list in `vision/training.json` (single-type photos; `packed` photos label every floor square, others use segmentation with a per-photo `label_threshold`: 10 for pale types, 20 for dark). `set2_yellow_grain` is excluded (partly packed: the background model takes the grain colour as floor). Leave-one-photo-out check with 16 photos: oval seed 95%, white rice 88%, macaroni 65%, long seed 55%, tiny seed 46%, yellow rice 45%, background 69% (empty floor most often misread as tiny seed/yellow rice/macaroni). `set4_white_rice`, `set5_white_rice` and `set5_yellow_balls` (scattered pale objects) are excluded: under the side light the brightness change across the dish exceeds the difference between pale objects and white paper, so neither the background model nor a two-colour split labels them correctly (tried both). Tried an empty-dish reference (`samples/webcam_empty_dish.webp`) without a fixed spot (user can't mark one): subtracting it works for the dense yellow balls but fails for others, because the grey reflections in the dish floor (likely the camera mount) shift when the dish moves 2–6 mm. Root cause of most vision trouble is those reflections; suggested fix: a matte black card around the lens so the dish reflects plain black, then an empty-dish reference becomes usable. On `set3_mixed` (the realistic mix): tubes, black grains, red seeds right; dark seed over-counted (35%), white rice almost missed (2%) because both rice training photos are packed while rice in a mix is separate translucent grains. Needs spread-out rice and yellow-grain photos. Model files in `vision/models/` are git-ignored; retrain in ~1 min. `pile_types.py predict --json` writes the estimate (share of each type). `vision/types.json` holds each type's reference width (mm): macaroni 5.3, oval seed 3.8, long seed 2.5, yellow rice 2.3, white rice 2.1 (rough), tiny seed 1.4, yellow balls 1.4 (rough, from ball spacing in packed photos). `filter_plan.py --estimate` (coarse mode) drops types under `--min-share` (5%), then picks the rig that gives the widest types their own fraction first, then most groups, then widest gap. On set3_mixed with placeholder holes: 5 / 3 / 1.5 mm -> macaroni | oval seed | long seed + yellow rice | tiny seed through; closest call macaroni 5.3 vs 5 mm hole. A marked fixed spot plus `dish_center_px` in calibration.json is still the most robust option for the demo; `--dish-center X Y` overrides.

First full webcam set (`samples/webcam_set1_*.webp`, red light, white paper): spread-out objects measure well; packed or piled dishes (couscous, white rice, mixed) fail because the background model needs visible empty floor, and touching objects merge. Rough sizes (median length × width, mm): red seed 6.3 × 3.8, oat grain 7.0 × 3.5, small dark seed 2.0 × 1.4, pasta tube 6.7 × 5.3. On `samples/webcam_white_01.webp` with `--dish-center 893 610`: 8 of 9 objects found (rice only partly), 2 false blobs from a light streak on the wall. `vision/dish_sizer.py`: Hough circle gives only the dish centre (it locks onto different rings); the search uses dish-sized radii in mm, relaxes edge thresholds for faint rims on white paper, ignores circles that don't fit in the photo (rulers create border-centred ones) and takes the median of the top candidates. Analysed area is `--floor-mm` (default 48) around it. Background = quadratic surface per CIELAB channel refit 4x without outliers. Darkening is down-weighted (`--shadow-weight` 0.5), lightening is not (pale objects). Status on the phone photos (tan desk, ceiling lights): rice, red seed, small seeds, black grain OK; big pale curved pasta fragments; oat grain partly missed; ceiling-light reflection on the dish wall becomes a false object; touching objects merge (tube + black grain). Further tuning on these photos has hit its limit — next step is the photo setup (backlight best, else matte coloured background + diffuse light, fixed overhead camera, full resolution), then touching-object splitting (watershed) since the real dish has several of each type.

`vision/filter_plan.py` reads dish_sizer's objects JSON and writes the plan JSON the arm planner will consume (`rig: {top, middle, bottom} -> filter id`). An object is caught by the first filter (top→bottom) whose hole <= its width. Modes: `split` (default; maximise non-empty fractions, then the log-ratio gap between any width and any hole) and `target MIN MAX` (coarsest hole <= MIN catches, finest hole > MAX guards above; filters in between are excluded). User wants target mode selectable by a microcontroller button later. Hole sizes in `vision/filters.json` (calipers, 2026-10-25): F1 = 2.5 mm (code A), F2 = 2.0 mm (B), F3 = 1.0 mm (C). F4 = 4.5 mm and F5 = 1.7 mm are the suggested targets for the two filters being printed (design ~0.2 mm larger; printed holes come out small), listed under `planned`; `filter_plan.py --made-only` leaves them out. Grain widths in types.json are best guesses (user couldn't measure; photo widths run wide from edge blur): long seed 2.0, yellow rice 2.1, white rice 1.9 mm. With all 5, coarse mode on set3_mixed picks 4.5 / 2.5 / 1.7: macaroni | oval seed | long seed + yellow rice (+ white rice) | tiny seed + yellow balls through; closest call 18%. F2 (2.0 mm) sits right on the grain widths, so it splits them unpredictably. Inseparable by size: tiny seed vs yellow balls, and the three grains. 2D width ignores thickness, so flat objects may pass a filter their measured width says they wouldn't.
